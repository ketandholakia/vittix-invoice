## Important Rules

- Do not invent existing APIs, classes, database tables, fields, or configuration.
- Inspect the repository before making assumptions.
- Reuse existing services, repositories, helpers, and utilities where appropriate.
- Do not introduce duplicate functionality.
- Do not remove existing functionality unless explicitly requested.
- Keep backward compatibility in mind.
- Follow the project's existing naming conventions.
- Keep changes focused on the requested task.

## Workflow

For every coding task:

### Step 1 - Understand

Inspect:

- project structure
- relevant source files
- existing documentation
- tests
- configuration
- database schema where relevant

### Step 2 - Plan

Before making substantial changes:

- identify affected files
- explain the proposed approach
- identify risks
- identify tests that should be added or updated

### Step 3 - Implement

Make the smallest clean implementation that satisfies the requirement.

### Step 4 - Validate

Run the appropriate:

- compiler/build
- unit tests
- integration tests
- static analysis
- formatting/linting

### Step 5 - Report

Summarize:

- files changed
- functionality added/changed
- tests executed
- test results
- remaining issues

## Safety

Never perform destructive operations without explicit approval.

Do not:

- delete databases
- delete project directories
- reset Git history
- force-push
- remove large groups of files
- overwrite configuration blindly

If a destructive operation appears necessary, stop and ask first.

## Git

Before making large changes:

- inspect git status
- inspect recent commits
- understand the current branch

Do not commit unless explicitly requested.

## Existing Architecture

Treat the current Vittix architecture as authoritative.

Do not replace existing infrastructure with a new framework/library simply because another approach appears newer.

First understand why existing infrastructure exists.

## Database

Database changes must be handled carefully.

Before changing schema:

1. inspect current schema
2. inspect migration/version mechanism
3. inspect existing database access code
4. identify compatibility implications
5. update tests

Never silently change production database structures.

## Tests

Tests are part of the implementation.

When changing existing functionality:

- locate existing tests
- update them when required
- add regression tests for bugs
- run the relevant test suite

Do not claim tests passed unless they were actually executed.

## Communication

Be concise but technically precise.

When a task is ambiguous:

- inspect the repository first
- make reasonable assumptions when safe
- ask only when a decision materially affects implementation

Do not blindly execute a requested approach if repository evidence indicates it would break the architecture.

## Priority

Priority order:

1. User requirement
2. Existing project architecture
3. Existing project documentation
4. Existing tests
5. Minimal safe implementation
6. Code quality
